# Passkey session and refresh acceptance

Five shared lifecycle cases run through Playwright and randomized Cucumber in real Chrome/Edge, separately from the seven baseline passkey cases. Each invocation owns its account, enrollment, virtual credential, browser contexts, and tokens. Enrollment uses the existing enrollment client, then a fresh browser profile imports only the explicitly owned virtual credential for the login client.

The browser lesson continues to clear local sign-in at access-token expiry and performs no silent refresh. The expiry case observes identity before expiry and clearing afterward, then requires a new submitted signed WebAuthn assertion in the same browser despite retained provider cookies; no password fallback is permitted. Refresh is exercised by the runner’s private request context, not by a new UI refresh feature. A successful refresh preserves subject/username and the login client’s issuer/audience, and remains rejected at all three business APIs with a valid customer certificate. Logout must invalidate refresh. Another public client must reject the captured refresh token, followed by a successful same-token correct-client control. Actual client-session expiry must reject refresh and leave the lesson signed out.

Only lifecycle fixtures in a fresh disposable `magic-shop-auth-*` project override `passkeys-spa` access-token lifetime to 20 seconds and client-session maximum to 45 seconds. Realm policy, the enrollment client, and other clients are unchanged. The existing TOTP policy implementation is shared through an explicit two-client allowlist. Ownership is privately recorded before mutation, null values remove owned Keycloak attributes during restoration, and readback verifies restoration after each selection. Pre-existing overrides or unexpected drift fail closed. Fixture cleanup and full project teardown run on failure as well as success. Tokens, private virtual-credential material, raw failures, and attachments remain excluded from reports.

The executable inventory requires 148 protocol executions (128 baseline + 20 passkey lifecycle), plus 48 separate Password/TOTP executions, for 196 total. Five lifecycle cases × two browsers × two runners add 20 executions, not 20 distinct behaviors. Dedicated `passkeys-lifecycle` and `passkeys-lifecycle-cucumber` phases prevent baseline reports from satisfying lifecycle requirements. The runner used Chrome 155.0.8059.84, Edge 154.0.4258.62, and Playwright 1.61.0. Eighteen focused tests passed for policy scope/private ownership/partial recovery/restoration/drift, report filtering, phase/count completeness, runner coverage, and failure cleanup. Syntax and whitespace checks passed.
