# SAML broker session and refresh acceptance

Six shared lifecycle checks run through Playwright and randomized Cucumber in real Chrome/Edge, separately from the 15 baseline SAML checks. Each invocation owns its provider/broker account, browser context, SAML response, and token material.

The browser lesson retains its existing policy: access-token expiry clears local identity without silent refresh. Re-entry preserves provider cookies but requires a new accepted SAML response and broker tokens for the same subject/username and exact reviewer role. The helper supports the pinned provider’s initial and password-only reauthentication forms, verifying the owned read-only username before entering its password when needed. Provider SSO reuse is permitted; the test does not claim expiry always forces an upstream credential prompt.

Private runner requests exercise the broker’s OIDC refresh grant. Separate cases verify that refresh preserves the exact lesson reviewer role for a mapped account and does not introduce a role for an account whose provider fixture has no lesson-role value. Both retain issuer/client/audience checks and rejection at all three business APIs with a valid customer certificate. Successful refresh must preserve the subject/username and issue a different access token, without a new front-channel SAML response. Other checks require browser logout to invalidate the broker refresh token, another valid public client to reject it followed by a successful same-token correct-client control, and actual broker-client session expiry to reject refresh and leave the lesson signed out.

Only lifecycle fixtures in a fresh disposable `magic-shop-auth-*` project override `lesson-saml` / `saml-spa` access-token lifetime to 20 seconds and client-session maximum to 45 seconds. Provider/realm lifetimes and other clients are unchanged. Server lifetimes are checked; these lifecycle cases do not alter clocks, assertions, or token claims. The policy helper allowlists four lesson clients, privately records ownership before mutation, explicitly removes owned lifetime attributes with null values, and verifies restoration. Pre-existing overrides and drift fail closed. Cleanup restores policy and removes owned accounts from both provider and broker realms after each group and on exit. The pre-existing `account-console` public client in the SAML broker realm is validated for the client-binding negative and is not modified.

Separate `saml-lifecycle` and `saml-lifecycle-cucumber` report phases prevent baseline reports from satisfying the new requirements. Reports retain only allowlisted names/statuses, excluding passwords, assertions, signing keys, access/refresh tokens, raw failures, and attachments. The inventory requires 192 protocol executions (168 previous + 24 SAML lifecycle) plus 48 separate Password/TOTP executions, for 240 total. SAML itself requires 84 executions. Counts describe browser/runner executions, not distinct behaviors.

The runner used Chrome 155.0.8059.84, Edge 154.0.4258.62, and Playwright 1.61.0. Twenty-eight focused tests passed for policy scope/private ownership/partial recovery/restoration/drift, report filtering, phase/count completeness, runner coverage, and lifecycle failure cleanup. Syntax and whitespace checks passed.

## Passkey readiness correction discovered during native acceptance

The two native attempts at SAML source `88b4ba8` failed before SAML lifecycle execution: Chrome’s altered-signature submission poll in attempt 1, and the first enrollment case in attempt 2. The latter attempt passed altered-signature rejection. The pinned Keycloak 26.4.0 templates attach registration/authentication click handlers through imported ES modules. A button can be visible before its module finishes loading.

A separate disposable project, `magic-shop-auth-passkey-readiness-20261017`, uses controlled 1500 ms delays on the real public WebAuthn scripts. It does not stub credentials, signatures, browser cryptography, or server validation. Old-versus-ready Chrome Cucumber controls verified an expected failure in enrollment and altered-signature rejection with the old click timing, then a pass in each after waiting for the page load event. Safe Boolean diagnostics showed the old clicks occurred before document completion; the signature control had focus but no changed-signature submission, identity, or rejection page. The four control reports are separate from accepted matrix evidence and are not counted as four new cases. The private probe script `/tmp/passkey-readiness-probe.sh` and model variants `/tmp/passkeys-readiness-{control,fixed,production}.mjs` are retained locally; the permanent public-script latency fixtures are now in the committed shared passkey model and run through ordinary CI.

Source `161dc0309277fbffc5dce7146dad6c614e9ab3a5` waits for the visible button and the current document’s load event before clicking either WebAuthn control. The existing enrollment and invalid-signature cases now deliberately delay their respective real public scripts and require that delay to have applied. Signature tampering requires nonempty signature/client-data/authenticator-data/credential-ID fields and no browser error; empty/error-only forms cannot satisfy the mandatory changed-signature assertion. A handled token-capture promise prevents secondary page-close rejection from masking an enrollment failure; the awaited token/identity/API assertions remain mandatory.
