# Assess authentication across a folder of projects

Use for an explicitly requested multi-project discovery and test-planning task. Inventory all authentication mechanisms found; use this skill's implementation guidance only for the mechanisms it covers. Do not turn every project into OIDC or prescribe Keycloak for an unrelated existing provider. This assessment does not authorize implementation, container execution or provider changes.

Discover repositories and independently deployed applications beneath the supplied root. Explain how monorepos, nested applications and shared authentication services were grouped. Skip generated/vendor/dependency/build directories and do not follow links outside the supplied root without authorization. Prefer manifests, auth middleware/adapters, routes, proxy config, Compose, IaC, CI and existing tests. Do not print secret values or collect token dumps.

For each project, identify browser vs server/API boundaries and observed mechanisms: OIDC/OAuth2, SAML, cookie/session, password/MFA, passkeys, Kerberos, client certificates/mTLS, API keys, service credentials, custom auth, or no authentication found. A dependency or sample config alone is weak evidence. Trace executable wiring and distinguish configured, used and unverified. Cite file/line evidence, confidence, gaps and questions. Separate user authentication, OAuth client authentication and API authorization. Identify broker/upstream exchanges and distinct certificate/token bindings where present.

When reference-style evidence is requested, read [recorded container requirements](recorded-container-tests.md). Plans must include desktop/VNC viewing, automated container execution, every browser-scenario recording and the local matrix/video report, not merely test cases. Label API-only evidence accurately. Do not claim the reference's automated jobs already use its manual desktop without checking.

Deliver a cross-project comparison, a per-project plan and dependency-ordered rollout. For each plan include architecture, owned fixtures/trust, applicable happy/negative/lifecycle cases, intended browser/runner/persona matrix, concrete proposed file locations, entrypoints and artifact layout, evidence/privacy/completeness gates, teardown and acceptance criteria. Identify reusable harness pieces separately from provider-specific adapters. Prioritize a first pilot based on concrete readiness and value; explain blockers without halting independent assessments. Mark proposed commands as proposed, and execute nothing to establish acceptance unless requested.
